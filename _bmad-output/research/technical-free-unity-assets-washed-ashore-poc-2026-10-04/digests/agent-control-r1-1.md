## Play-mode verification without screenshots (what works, caveats)
- **Works:** UTF PlayMode tests run from the command line (`Unity.exe -batchmode -projectPath . -runTests -testPlatform PlayMode -testResults r.xml -logFile log.txt`). They produce NUnit XML and a non-zero exit code on failure. Assertions are code-level: load the scene, add a Keyboard/Mouse with InputTestFixture, `Press(keyboard.wKey)`, yield frames, then assert that the player transform moved, `CharacterController.isGrounded` is true, and so on.
- **Works:** in a live Editor, `unity command editor_play`, then `unity command eval` to read transform positions or `Time.frameCount` across calls, plus `unity logs` to check for errors. Unity's own skill warns that an unfocused Editor can stall at frame 1 while status still says "playing", so the agent must check that frameCount or time advances.
- **Caveats:**
  - Play-mode entry and recompiles reload the domain and kill in-flight eval/MCP calls. Disabling domain reload is the common workaround for MCP bridges.
  - Compile errors at startup put the Editor in Safe Mode and stop the CLI from connecting.
  - The official UTF docs say nothing about `-nographics` with PlayMode tests. Community reports use it to avoid GfxDevice crashes, but rendering-dependent code such as terrain rendering, cameras, and GPU work won't be exercised.
  - Batchmode needs an activated license. Licensing wasn't verified this run.
  - Sources don't say whether `-batchmode` alone (without `-nographics`) is the safer default for physics/CharacterController tests. That is unverified.
